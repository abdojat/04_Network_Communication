## 1. الهدف والسيناريو

يعالج المخبر تبادل كائن يمثل ملف مشتريات عميل بين خدمات موزعة. يحوي الملف اسم العميل والمدينة والمشتريات والأسعار وأهلية العروض، مع وجود رمز خصم مؤقت يجب عدم نقله. تهدف التجارب إلى تطبيق JSON وJava Object Serialization وGoogle Protocol Buffers، مع تفسير اختلاف المخطط الهيكلي وحجم الحمولة وإمكانات التوافق. تم الاعتماد على مشروع HTTP Server/Client المرفق وإكمال دواله الناقصة، مع الاحتفاظ بمساري `/task` و`/status` وإضافة مسار `/api/analyze` لإرسال JSON.

## 2. التجربة الأولى: JSON

**المهمة 1.1:** أُنشئ الملف `lab/customer_request.json` وفق مثال الورقة: الاسم Ahmad Saleh، المدينة Damascus، طلبان سابقان، ثلاث مشتريات وأسعارها، وأهلية العروض `true`. يرسل `JsonLab.java` أو `curl.exe` الملف عبر HTTP POST إلى السيرفر المعدّل، مع ترويسة `Content-Type: application/json`. في الاختبار المحلي أعاد السيرفر الحالة `HTTP 200` والرسالة `received: true`، وكان حجم ملف JSON المنسق **312 بايت**. يقوم المسار المضاف بإعادة الحمولة كما استلمها للتدريب على النقل؛ وهو **لا يفرض JSON Schema ولا ينفّذ تحليل مشتريات تجارياً**.

**المهمة 1.2:** يرسل الطرف الأول `["1200", "25", "85"]` بوصفها قيماً نصية، في حين يتوقع الطرف الثاني `[1200.00, 25.00, 85.00]` بوصفها أرقاماً. يشبه الشكلان بعضهما بصرياً، لكن نوع كل عنصر يختلف. نفّذ `SchemaMismatchLab.java` فحصاً محدوداً على مثال الورقة، فأظهر الخطأ المتوقع: `Schema mismatch: expected JSON number, got "1200"`. وعند استعمال البيانات الرقمية الصحيحة احتسب الناتج `2550000.000000`.

**إجابة سؤال التقرير (1):** لا يستطيع مهندس الصيانة معرفة الطرف الصحيح بمجرد رؤية JSON أو الاستثناء؛ لأن JSON وحده لا يحدد أي عقد أنواع بيانات يجب أن يتفق عليه المرسل والمستقبل. قد تكون المشكلة في المرسل الذي غيّر نوع القيمة أو في المستقبل الذي اعتمد توقعاً غير موثق. في نظام موزع كبير تؤدي هذه الفجوة إلى أخطاء توافق بين الخدمات، وتعطل الطلبات وصعوبة تتبع المصدر الصحيح مع تعدد الإصدارات. الحل هو اعتماد عقد مشترك موثّق، والتحقق من الأنواع، واختبارات توافق وإدارة إصدارات، ويمكن استخدام JSON Schema عند اختيار JSON.

## 3. التجربة الثانية: Standard Java Serialization

**المهمة 2.1:** طُبقت الواجهة `Serializable` على `CustomerProfile.java`، مع الحقول الأساسية `customerName` و`purchasedItems` و`itemPrices` و`isHolidayDealEligible`، بالإضافة إلى `systemVersion` من نوع `static` و`tempDiscountToken` من نوع `transient`. أضيف الحقل `address` لتجربة الاستثناء، ويكون فارغاً أثناء التسلسل الطبيعي.

**المهمة 2.2:** استخدمت `ObjectOutputStream` لتحويل الكائن إلى `byte[]`، و`ObjectInputStream` لإعادة بنائه. في اختبار OpenJDK 21 كان الحجم **345 بايت** لهذا الكائن. قبل التسلسل ظهر الرمز `SECRET-TOKEN-999` والإصدار `v2.4`. بعد استعادة الكائن ظهرت قيمة `tempDiscountToken = null`، وبقي `systemVersion = v3.0-UPDATED` بعد تغيير قيمته. السبب أن `transient` يمنع تسلسل قيمة الحقل، أما `static` فهو حالة مشتركة على مستوى الصنف ولا يدخل في حالة الكائن المرسلة.

**المهمة 2.3:** أُنشئ الصنف `Address` من دون `implements Serializable`، ثم أُسند كائن منه إلى حقل داخل `CustomerProfile`. أسفرت محاولة التسلسل عن `java.io.NotSerializableException: Address`، وهو السلوك المتوقع. عند إعادة الحقل إلى `null` نجح التسلسل، وأظهر تفحّص البايتات وجود النصين `CustomerProfile` و`customerName` داخل الحمولة. لذلك لا تعد صيغة Java الثنائية تشفيراً يحمي الهيكلية أو القيم، كما يُنصح بعدم فك تسلسل بيانات Java غير موثوقة المصدر.

**ملاحظة:** يتضمن المثال الأصلي مُنشئاً فارغاً، لكن تنفيذ `Serializable` على الصنف ذاته لا يفرض وجود مُنشئ بلا معاملات؛ توجد قواعد منفصلة للمُنشئ في أصناف الأساس غير القابلة للتسلسل.

## 4. التجربة الثالثة: Google Protocol Buffers

**المهمة 3.1:** أُنشئ `lab/proto/customer_profile.proto` حسب الورقة باستخدام `proto2` وبحقول ذات علامات رقمية ثابتة: `customer_name = 1` و`city = 2` و`purchased_items = 3` و`item_prices = 4` و`is_holiday_deal_eligible = 5`. تم توليد الصنف `CustomerProfileProto.java` بمترجم `protoc` وتضمينه في المشروع.

**المهمة 3.2:** يبني `ProtobufLab.java` الرسالة بنمط `Builder`، ويحوّلها عبر `toByteArray()` ويعيدها بواسطة `parseFrom()`. يطبع اسم العميل والمدينة الافتراضية. رغم أن `getCity()` يعيد `Damascus` حسب قيمة `default`، فإن `hasCity()` يكون `false` ما دام الحقل لم يُرسل فعلياً. تم التحقق من المخطط وحجم الحمولة باستخدام `protoc 3.13.0`؛ وبلغ الحجم **35 بايت** للحقول الأربعة المشتركة. يتطلب تشغيل صنف Java المولَّد مكتبة `protobuf-java` التي يجلبها Maven، ولم يتوفر هذا الاعتماد لاختبار برنامج Java Protobuf في بيئة إعداد التقرير.

**إجابة سؤال التقرير (2)، مقارنة الأحجام:** استخدمت المقارنة **الحقول المنطقية المشتركة نفسها**: اسم Ahmad Saleh، العنصران Laptop وMouse، السعران 1200 و25، وأهلية الخصم `true`، من دون إرسال مدينة اختيارية أو رمز جلسة مؤقت. النتائج:

| طريقة الترميز | حجم الحمولة في الاختبار |
|---|---:|
| JSON مضغوط بنص UTF-8 | 118 بايت |
| Java Object Serialization (OpenJDK 21) | 345 بايت |
| Google Protobuf (protoc 3.13) | 35 بايت |

النتيجة خاصة بهذا المثال وبنسخ الأدوات المستخدمة، ولا تعني أن Protobuf سيكون دائماً الأصغر مع جميع المدخلات. كما أن انخفاض حجم الرسالة ليس دليلاً على وجود تشفير.

**إجابة سؤال التقرير (2)، إعادة التسمية:** تغير اسم الحقل عند المستقبل فقط من `customer_name = 1` إلى `client_full_name = 1`، من دون تغيير رقم الحقل أو نوعه. نجحت عملية فك التسلسل باستخدام `protoc`، واستعاد المستقبل `client_full_name: "Ahmad Saleh"`. السبب أن التمثيل الثنائي يعتمد **العلامة الرقمية ونوع القيمة** لا اسم الحقل في الشيفرة. يشمل المشروع مخطط المستقبل المعدّل وصنف Java المولَّد، مع `SchemaRenameLab.java` لاختبار ذلك عند تشغيل Maven على Windows.

## 5. أسئلة التقييم والمناقشة الختامية

**الحالة الأولى — متصفح JavaScript وخادم خلفي:** الخيار الأنسب هو **JSON**، لأنه مدعوم بصورة طبيعية في المتصفحات وواجهات HTTP، وسهل الفحص وتصحيح الأخطاء، وقابل للتبادل بين لغات مختلفة. يُفضّل التحقق من المخطط لحماية التكامل بين الطرفين.

**الحالة الثانية — نموذج أولي من ثلاث عُقد Java على JVM متوافق:** يصلح **Java Object Serialization** ضمن القيود المعطاة، فهو لا يحتاج مكتبات أو مترجمات إضافية ويسمح بنقل الكائنات بسرعة أثناء التطوير. لكنه مرتبط بجافا ويستلزم الحذر من فك التسلسل غير الآمن، لذلك لا يكون عادة الخيار الأنسب لنظام إنتاج مفتوح.

**الحالة الثالثة — تداول مالي متعدد اللغات مع قيود حجم صارمة:** الخيار الأفضل من الخيارات الثلاثة هو **Protocol Buffers** لأنه متعدد اللغات، وله مخطط صريح وحمولة ثنائية أصغر عادة. لتحقيق الأمان المطلوب يجب إضافة **TLS/HTTPS أو mTLS** والمصادقة والتفويض والتحقق من المدخلات؛ Protobuf بحد ذاته لا يشفر الرسائل.

**السؤال الإضافي — لماذا لا يعاد استخدام رقم Tag محذوف؟** لأن مرسلاً قديماً قد يستمر في إرسال رقم الحقل القديم. إذا أعيد استخدام الرقم لمعنى جديد فقد يفسره مستقبل جديد خطأً وكأنه قيمة الحقل الجديد، ما يسبب فساداً صامتاً في البيانات. للحفاظ على التوافق يجب حجز الأرقام المحذوفة باستخدام `reserved` في ملف `.proto`.

## 6. النتيجة العامة وحدود الاختبار

أظهر الاختبار العملي نجاح اتصال HTTP بين عميل المشروع الأصلي وعقدتين، وكذلك إرسال JSON، وكشف اختلاف الأنواع، وتسلسل Java وإعادة بنائه والاستثناء المتوقع. وأُثبت بوساطة `protoc` نجاح نقل بيانات Protobuf وإعادة تسمية الحقل مع ثبات رقم العلامة. يشمل المشروع كود Protobuf المولَّد ومكتبة التشغيل معرفةً في Maven، لكن تشغيل برنامج Java الخاص بـProtobuf يحتاج تنزيل الاعتماد وتشغيل `run_all.ps1` على جهاز الطالب. يُنصح بإضافة صور للمخرجات الفعلية من Windows قبل التسليم إن كانت مطلوبة من المدرّس.
